# Break the Wall in Claude and ChatGPT through MCP

Date: 2026-10-27. Scope: research before planning an integration with AI assistants. No app source, configuration or dependency on `main` is changed; the prototype lives on the local branch `spike/mcp` (commit `9a8914b`), which is not pushed or merged.

## Why this research

The owner wants the next release to integrate the app with ChatGPT and Claude ("Integrare l'app con ChatGPT e Claude Code … l'integrazione è fondamentale e risulta più facile provare l'app"). Two ideas were on the table: embedding the assistant inside the app and capturing its text, or an MCP server or plugin. The agent advised against embedding (separate desktop apps cannot be embedded; embedding their websites means handling third-party sign-ins and scraping a page that changes; and it would turn the product towards a chatbot, which the [product identity](../../product.md#identity) rules out). The owner chose MCP ("sisi, MCP").

The question for this research: can an assistant hand a text to Break the Wall (level A), and can the assistant's own model write a disassembly that Break the Wall checks (level B)?

## What the clients support (checked 2026-10-27)

| Client | Local MCP server (stdio, on the user's computer) | Notes |
|---|---|---|
| Claude Code | Yes: `claude mcp add`, or a `--mcp-config` file | Installed on the owner's Mac (2.1.303); used for the experiment |
| Claude Desktop | Yes: a JSON configuration, or one-click **Desktop Extensions** (`.mcpb`, a zip with the server and a `manifest.json`; Claude Desktop ships its own Node.js, on macOS and Windows) | Anthropic recommends remote servers for its directory; `.mcpb` files distributed privately are updated by hand ([Anthropic: desktop extensions](https://www.anthropic.com/engineering/desktop-extensions), [MCPB docs](https://claude.com/docs/connectors/building/mcpb)) |
| ChatGPT | **No direct local server.** Custom MCP connectors need Developer Mode and a remote HTTPS server, or OpenAI's tunnel for local development | Which plans may use it, and whether they can write or only read, is reported differently by different sources; to be checked against OpenAI's help center ([OpenAI: connect from ChatGPT](https://developers.openai.com/apps-sdk/deploy/connect-chatgpt)) |

The official TypeScript SDK (`@modelcontextprotocol/sdk`) is at 1.32.2, published four days before this note; the prototype does without it.

## The prototype

- **In the app** (`spike/mcp`): the main process listens on a local socket (`<userData>/incoming.sock`, mode 0600; a named pipe on Windows). Each line is `{ title, text, question }`; the host imports the text exactly like a paste (`importSource`, with the same limits), sends it to the renderer, and brings the window to the front. The library adds the source to the Studio draft, sets the question and opens Studio. The learner then picks the route and generates as usual.
- **The MCP server** (`spike/mcp/server.ts`, bundled with esbuild to one 0.8 MB file): stdio JSON-RPC written by hand (`initialize`, `tools/list`, `tools/call`), with three tools:
  - `open_in_break_the_wall(text, title?, question?)`: level A. If the app does not answer, it launches it and retries for 15 s.
  - `start_disassembly(text, title?, question, language)`: level B. Returns the app's own structure instructions, the numbered source and the JSON schema (`STRUCTURE_INSTRUCTIONS`, `buildStructureInput`, `structureJsonSchema`).
  - `submit_structure(json)`: level B. Runs the app's own phase-1 check (`acceptStructure`: schema, levels, joints, citations, bill of materials, lengths, language) and returns "accepted" or the repair request the app sends its models (`buildRepairRequest`).

## Results

| Check | Client and model | Result |
|---|---|---|
| Handshake | `initialize` and `tools/list` over stdio | **passed** |
| Level A | Claude Code `-p`, asked to explain HTTPS certificate validation and open it in Break the Wall | **passed**: the tool opened Studio in the running app with the text (31 lines) and the question; 3 turns, $0.07. A first call, whose output the agent misread, had also arrived: Studio showed both sources |
| Level B, Atlas runbook (English, 177 lines) | Claude Code `-p`, model `claude-sonnet-5-5` | **accepted on the first attempt**: 7 parts, lines 1–6 excluded as context and 174–177 as outside the question, every line accounted for; 5 turns, $0.18, 42 s |
| Level B, Mill (Italian, 131 lines) | same | **accepted on the second attempt**: the first had four texts over their limits (two joint labels of 25–26 characters for 24, two roles of 103 for 100); the model fixed them from the app's findings; 6 turns, $0.21, 50 s |

Two level B runs are a signal, not a measurement. They cover only phase 1 (structure); phases 2 (content per part) and 3 (runs and reassembly) were not tried.

## What it means

- **Level A is cheap and works today with Claude.** The app needs a local entry point (the socket) and the Studio hand-off; the MCP server needs one tool. It also gives a way in for anything else (a URL scheme, a command line).
- **Level B is the strong idea, and phase 1 already works.** The assistant's model does the writing, on the user's own Claude plan, while Break the Wall keeps what makes it trustworthy: its checks and the bill of materials. The app's existing phases, instructions, schemas and repair messages carry over unchanged; the work is to drive phases 2 and 3 the same way and to save and open the result.
- **ChatGPT needs a different shape.** Without a remote server, ChatGPT cannot call a server on the user's Mac. Options: a small remote server (hosting, authentication and the source leaving the Mac, which conflicts with the privacy story), OpenAI's tunnel (a developer route, not for learners), or waiting. Claude first.

## Constraints and risks

- **Distribution.** The server must run without the user installing Node: as a `.mcpb` for Claude Desktop (which ships Node), and for Claude Code as a command that runs the server with the app's own Electron in Node mode (`ELECTRON_RUN_AS_NODE=1`) or a bundled script; to be decided in the plan.
- **Security.** Any local process of the same user could write to the socket. The socket is user-only (0600), the text goes through the same import checks as a paste, and nothing is generated or sent anywhere until the learner presses Generate in level A. Level B saves a disassembly only after the app's own checks.
- **The privacy promise changes for level B.** The source goes to Anthropic through the user's Claude client; the app must say so, as it does for ChatGPT.
- **Tool descriptions steer the model.** The model used the tools correctly from their descriptions alone; wording matters and should be tested.
- **The SDK.** The hand-written protocol was enough for three tools; the plan should decide between it and the official SDK (dependencies, protocol versions, future features such as MCP Apps).
- **Scope for one week.** Level A with a Claude Desktop extension and Claude Code instructions fits; level B for all three phases is the stretch goal; ChatGPT does not fit.

## Recommendation

Plan the integration in this order: level A for Claude Code and Claude Desktop (socket in the app, the MCP server shipped with the app, a `.mcpb` for Claude Desktop, instructions for Claude Code), then level B for all three phases, saving the result as a generated disassembly whose provider records the assistant. Keep ChatGPT for a later plan, after deciding whether a remote server fits the privacy promise.
