# How far the app is from Windows

Date: 2026-10-27. Scope: research before planning a Windows alpha. No app source, configuration or dependency on `main` is changed; the experiment ran on the throwaway branch `spike/windows-ci`, which is not merged.

## Why this research

After the macOS DMG, the owner asked whether a Windows alpha is the urgent next step ("forse un'urgenza è l'alpha per Windows"). No user has asked for Windows yet, and the code has never run there: tests and CI run only on macOS. The owner agreed to measure first ("ok, procedi").

## The experiment

A temporary workflow (`.github/workflows/windows-spike.yml` on `spike/windows-ci`, commit `4680dc9`) ran on `windows-latest` (image `windows-2025-vs2026`), Node 22.23.2 and npm 10.9.8, run 40532360535. Every step continued on error so one run shows every failure.

| Step | Result |
|---|---|
| `npm ci` | **passed** |
| Types (`npm run typecheck`) | **passed** |
| Tests (Vitest) | **2 failed, 324 passed** of 326 (macOS runs 338: the 12 extra are local-only private fixtures, skipped in CI on both systems) |
| Build (Vite and esbuild) | **passed** |
| Start from source with `BTW_SMOKE_TEST=1` | **passed**: "start check: the library is drawn", exit 0 |
| Package with `@electron/packager` for `win32`/`x64` | **passed**: `Break the Wall-win32-x64`, 365 MB unpacked |
| Start of the packaged `Break the Wall.exe` | **passed**: "start check: the library is drawn", exit 0 |

## What fails, and why

Both test failures are in the tests, not the app. They write POSIX paths that Windows resolves differently:
- `tests/app-files.test.ts` builds its root as `/Applications/…`; on Windows `path.resolve` turns it into `D:\Applications\…`, so `appFilePath` correctly refuses a path that no longer starts with the given root. The packaged start check proves the real resolution works: there the root comes from `resolve(__dirname, '../dist')`.
- `tests/eval.test.ts` checks `resolve(folder, s.path).startsWith(folder + '/')`; on Windows the separator is `\`. The rule (public case sources stay in the public folder) holds; the test needs `path.sep` or `path.relative`.

## What the run does not show

- **Credentials.** `safeStorage` on Windows uses DPAPI, not a keychain. Sign-in, storage and sign-out have not run there.
- **Files, dialogs and local models.** The source picker, `.txt`/`.md` import, and local model detection on `127.0.0.1` have not run on Windows.
- **Appearance.** The start check reads the page; nobody has looked at fonts (the stacks fall back to Segoe UI), scroll bars, or the window frame.
- **Install.** The packaged folder is not an installer. There is no Start menu entry or uninstaller.
- **SmartScreen.** An unsigned `.exe` downloaded from the internet shows "Windows protected your PC" until the user chooses "More info" → "Run anyway"; its exact steps on Windows 11 must be seen on a real download.
- **Windows on ARM**, and Windows 10.

## What the app says that is wrong on Windows

The interface names the Mac in 7 strings per language (`src/renderer/i18n/en.ts`, `it.ts`): "on this Mac", "this Mac's keychain", "Models on this Mac", "the source stays on this Mac", and the keychain messages. On Windows they need neutral or platform-aware wording ("this computer", "Windows' credential protection"). The code itself has three `darwin` branches in `main.ts` (window icon, Dock icon, keeping the app open after the last window), all already right for Windows.

## Options for a Windows alpha

| Choice | Option | Notes |
|---|---|---|
| Format | Portable zip | No installer and no dependency; the user extracts and runs the `.exe`. No Start menu entry; SmartScreen still applies to the extracted file. |
| Format | Squirrel installer (`electron-winstaller`, Electron project) | Per-user install without administrator rights, Start menu and desktop shortcuts, an uninstaller, and the format Electron's updater uses later. One development dependency. |
| Format | NSIS installer through `electron-builder` | Flexible installer; a much larger dependency tree. |
| Signing | Unsigned | SmartScreen warning with "More info" → "Run anyway", like Open Anyway on macOS. |
| Signing | Microsoft's cloud signing service or a code-signing certificate | Removes or reduces the warning; a monthly or yearly cost, and eligibility for an individual in Italy has to be checked. |
| Architecture | x64 | Covers most Windows PCs; arm64 later. |

## Constraints and risks

- A witnessed install needs a Windows PC; CI can build and start the app, not judge its appearance or SmartScreen.
- Data would live in `%APPDATA%\Break the Wall` (the app name is set before anything else, as on macOS).
- Windows CI roughly doubles the CI minutes per change if added to every pull request; free for a public repository, but slower feedback.

## Recommendation

The distance is short: the app already builds, starts and draws the library on Windows, packaged or not. A small plan is justified, in this order: make the two tests path-neutral and add a Windows job to CI so it stays that way; make the interface's Mac wording platform-aware in both languages; package an x64 installer (Squirrel recommended) in the Release workflow next to the DMG, unsigned for the alpha, with the SmartScreen steps in the README; and a witnessed install on a Windows PC. Whether to start now depends on demand: no user has asked yet, and the owner needs a Windows PC for the last step.
